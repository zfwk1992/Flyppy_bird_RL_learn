Reinforcement learning, brieflyWhat the agent actually sees

The AI never receives your coordinates, your height, or the pipe distance as numbers. Its only input is four stacked 80×128 black-and-white frames — raw pixels, built from the same sprites and geometry that draw the canvas on the right, just smaller and binary. No hand-engineered features: velocity, gap position, everything it "knows" is inferred from how those four frames differ from one another.

It commits to one of two actions — flap or don't — every 4 frames, holding that choice for the whole window (frame_skip=4, frame_stack=4). A single frame can't even tell you which way the bird is moving; only the stack can.

The learning signalReward, and the Q-function

The reward is almost insultingly simple: +1 for clearing a pipe, −1 for dying, 0 otherwise. Everything the agent does — every twitch of the wing — is in service of maximizing the discounted sum of that signal over the rest of the episode.

It learns this through a Q-function, Q(s,a): "if I take action a right now, how much total future reward should I expect?" Acting is then just picking the higher of the two numbers every step — argmax Q(s,·). Training is Double DQN: one network picks the action, a separate slowly-updated target network scores it, which keeps the Q-values from drifting upward on their own optimism.

Why the network has two headsValue, advantage, and Q = V + A

Most frames don't matter. If the bird is centered in a gap with the next pipe still far off-screen, flapping or not flapping barely changes the outcome — what matters is the overall situation, captured by the state value V(s). Only in a narrow band of frames, right at a gap edge, does the choice of action carry real weight — the advantage A(s,a).

Splitting the last layer into these two heads means the value branch learns from every frame, regardless of which action was actually taken that step — instead of only the played action getting a gradient, as in a plain DQN. Subtracting the mean of A isn't optional polish: without it, V and A aren't uniquely determined by Q (add a constant to one, subtract it from the other, Q is unchanged), and the two heads drift apart during training.

The browser version you're playing against loads exactly these weights into a hand-written JavaScript forward pass — no ONNX runtime, no WASM blob, so the entire download is the weights themselves (fp16, 2.52 MB). 28 ms per decision, against a 133 ms budget.

Does it actually match the Python model?Verified, not assumed

Porting a trained model to a hand-written JS re-implementation is exactly the kind of change that silently degrades. So every layer of this port is checked bit-for-bit against the original: 1,200 reconstructed observation frames match the Python rendering pipeline pixel-for-pixel, and 300 sampled decisions match the PyTorch model's action for action (max Q-value deviation 4×10−3, from the fp16 weights). The parity harness ships in the repo — web/tools/ — and needs no Python to re-run.

Both numbers describe the same weights running two different code paths; the gap between them (standard error 14.8) is noise, not a regression — Flappy Bird scores are heavy-tailed (median 45.5, best run 322 pipes), so a single average understates how often it either dies early or nearly never dies. The human number comes from a small sample — take it as a rough sense of scale, not a rigorous baseline.

This is the same network architecture that, on an earlier version of the training pipeline, plateaued at 1.3 pipes after 100,000 episodes. The fix wasn't a better algorithm or more compute — it was finding and closing about a dozen structural bugs in the data pipeline (a terminal-state flag silently dropped 75% of the time, a target network stuck in training mode, a reward scale that saturated the loss function). Not every n-step or epsilon variant tried afterward helped either — n_step=3 made no measurable difference, and leaving just 1% random actions in at evaluation time (ε=0.01 instead of 0) dropped the measured score 6.2×. The write-ups for both the failures and the fixes are in the repo.
