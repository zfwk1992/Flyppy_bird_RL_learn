# 阶段 2 验收：观测管线与浏览器推理的一致性

阶段 1 证明了 **游戏** 的 JS 移植和 Python 逐位一致（见 [parity_game.md](parity_game.md)）。
阶段 2 要证明的是另外两件事：

1. **观测管线**：浏览器算出来的 80×128 二值图，和 `flappy_env._observe()` 一样
2. **推理**：手写 JS 前向算出来的 Q 值，和 PyTorch 一样

这两件事必须分开验。合在一起只看"AI 会不会飞"，一旦不对就没法定位 ——
观测差一格和权重读错，表现出来都是"AI 变笨了"。

## 结论

| 验的是什么 | 方法 | 结果 |
|---|---|---|
| 画面重建（288×512 R 通道） | 1200 帧逐帧比 md5 | **1200 / 1200 逐位一致** |
| 二值观测（80×128） | 1200 帧逐帧比 md5 | **1200 / 1200 逐位一致** |
| 帧栈（4×80×128） | 300 次决策逐次比 md5 | **300 / 300 逐位一致** |
| Q 值 | 300 次决策比 fp32 数值 | 最大偏差 **4.02e-3** |
| 动作 | 300 次决策比 argmax | **300 / 300 一致** |
| 浏览器 ≡ Node | 5 个 seed 逐局比最终分数 | **5 / 5 完全相同** |

Q 值那 4e-3 的偏差来自权重存成了 fp16，以及卷积累加顺序不同。
它没有翻掉任何一次 argmax —— 300 次决策里两个 Q 的差距最小也远大于 4e-3。

## 三个关键决定，以及为什么

### 1. 不从画布取像素，而是解析式重建画面

最直觉的做法是 `ctx.getImageData()` 把 AI 那块画布读回来。没这么做，三个理由：

- **阶段 3 要往画布上加东西**（计分板、边框、特效）。只要 AI 从画布取像素，
  任何纯视觉的改动都会污染观测 —— 改个边框颜色就能让 AI 变笨，
  而且这种 bug 从表现上完全看不出根因。
- **画布在 Node 里不存在**，读画布的实现就只能靠人眼看截图验，
  拿不到上面那张表里的 1200 帧逐位比对。
- **`drawImage` 在浮点坐标上会抗锯齿**，而 pygame 的 blit 是整数截断。
  两者本来就对不齐，读画布反而要额外处理这个差异。

所以 `web/obs.js` 按 `_draw()` 的顺序（背景 → 管道 → 地面 → 小鸟）
自己把 288×512 的 R 通道拼出来，可见画布只负责给人看。

### 2. 观测只需要 R 通道，而 R 通道等价于"有没有被不透明像素盖住"

`_observe()` 取的是 `pixels3d(SCREEN)[:, :, 0]` —— 只有红通道。
对本项目用到的五张精灵，实测（`export_obs_sprites.py` 里有断言）：

> `R > 1`、`任意通道 > 1`、`alpha > 0` 三者**逐像素完全相同**，
> 且不存在 alpha>0 但合成后 R==0 的像素。

所以合成到纯黑背景上时，画面里"亮"的区域就是精灵的不透明区域。
`web/assets/obs-sprites.js` 存的就是这五张图合成后的 R 通道（base64，共 75 KB）。

注意：**知道哪些像素亮还不够**，还要知道它们有多亮。见下一条。

### 3. INTER_AREA 是照着 OpenCV 的权重表实现的，不是"格子里有没有非黑像素"

一开始的计划是用覆盖判定近似 `cv2.INTER_AREA`（当时实测模型对此不敏感：
真实管线 81.25 根 vs 覆盖判定 75.83 根）。最后没用近似，因为算了一下发现
差异是**系统性**的，不是随机噪声：

- 缩放比是 288/80 = **3.6**，不是整数，所以输出列会跨到源列的一部分上。
  3.6 的倍数的小数部分只可能是 {0, .2, .4, .6, .8}，最小的非零重叠是 **0.2**。
- 一个格子覆盖 3.6×4 = 14.4 个源像素。最暗的精灵像素 R = **83**。
- 权重最小的那种情形：0.2 × 83 / 14.4 = **1.15**，四舍五入成 1，
  而阈值要求 `> 1` —— 所以 INTER_AREA 判它**灭**，覆盖判定判它**亮**。

也就是说管道左右边缘那一列，两种做法会稳定地差一格。既然照抄 OpenCV 的
权重表只要三十行（`web/obs.js: areaWeights`），就没有理由留这个已知偏差。
照抄之后 1200 帧一个像素都不差。

一个附带的坑：OpenCV 最后一步是 `saturate_cast<uchar>`，也就是 **cvRound
（.5 进偶数）**，不是 `Math.round`（.5 向上）。

## 为什么不用 onnxruntime-web

这个 demo 是发到 LinkedIn 上的，首屏体积直接决定有多少人会真的点开。
onnxruntime-web 的 wasm 运行时压缩后仍有几 MB。

而这个网络只有 3 个卷积 + 3 个线性层，没有 BatchNorm 也没有 Dropout，
一次前向约 **1230 万次乘加**，`frame_skip=4` + 30fps 意味着每秒只要 **7.5 次**。
手写前向实测：

- Node（桌面 CPU）：**28 ms / 次**，预算是 133 ms
- 总下载量：`weights_fp16.bin` **2.52 MB**，零运行时依赖

`web/model/flappy_dqn_fp16.onnx` 留着没删 —— 它是同一份权重的第三方可验证副本，
也是万一要换回 onnxruntime 的退路。页面不会加载它。

## 30 局实测

`node web/tools/ai_eval.mjs 30`（跑的就是浏览器 import 的那几个模块）：

```
平均        86.43 根   (标准误 14.77)
中位        45.5
最低 / 最高 4 / 322
```

原计划的验收标准写的是"平均落在 70–85"。86.43 落在区间外一点点，
但这个区间本身定得太死了：分数分布是**重尾**的（中位 45.5、最高 322），
30 局的标准误就有 14.77，和 Python 侧 100 局的 78.2 相差 8.2 根，
连半个标准误都不到，是纯粹的抽样噪声。

真正把这件事钉死的是上面那张表 —— 观测逐位一致、动作 300/300 一致，
JS 和 PyTorch 的差别只剩 fp16 的舍入。分数不同只是因为 seed 不同。
