# 12 · 怎么判断网络该多大

"网络是不是太小了？""要不要加层？"——这类问题在 RL 里几乎总是被**猜**着回答的。
这一篇讲怎么**测**：三个便宜的诊断，能把"该改网络"和"改网络没用"分开。

用的都是本项目真实跑出来的数据。

---

## 0. 先问一个更基本的问题：瓶颈在哪一环

改网络之前先确认瓶颈**确实在网络**。一条 RL 管线的能力受制于四个环节：

```
环境物理 ──> 观测(感知) ──> 网络(容量) ──> 优化(算法/超参)
```

任何一环卡住，加大网络都没用。本项目就是活例子：CNN 在 `gap 60-165` 上
稳定停在 17 根管道，我一度以为是网络容量或分辨率问题——**两个都不是**。

### 诊断一：完美状态对照（最有价值的一个）

**做法**：把感知整个拿掉，直接把游戏的真实内部状态喂给一个极小的 MLP。
如果连"上帝视角"都做不到，那瓶颈就在物理或算法，跟网络和感知无关。

本项目的实现是 [`experiments/state_mlp.py`](../../experiments/state_mlp.py)：
8 维状态（小鸟 y/速度 + 下两根管道的距离/缝隙中心/缝隙大小），
两层 128 的 MLP，**18,051 个参数**（CNN 的 1/70），训练代码复用主管线的
`skip_step` / `epsilon_at` / `sample_random_action`。

实测（100 局纯贪婪）：

| 分布 | CNN 1,260K 参数<br>80×80 像素 | **MLP 18K 参数<br>完美状态** | 差距 |
|---|---|---|---|
| gap 80–165 | 56.8 | **142.7** | **2.5×** |
| gap 60–165 | ~17 | **19.4** | 1.14× |

**这张表一次回答了三个问题：**

1. **网络容量不是瓶颈。** 1/70 的参数量在两个分布上都打赢了。
2. **宽缝上感知是瓶颈。** 完美状态带来 2.5 倍提升——这就是 CNN 因为
   "看不清"损失掉的部分，也给出了改进分辨率的**收益上限**。
3. **窄缝上感知不是瓶颈。** 只提升 1.14 倍，基本在噪声内。
   给了上帝视角也过不去，说明 60–80px 的缝隙是**控制/物理**的边界。

> 这个实验很便宜（MLP 训练比 CNN 快一个数量级，环境完全复用），
> 但能一次排除掉一半的猜测方向。**在动网络之前先做它。**

## 1. 诊断二：参数都花在哪了

```python
for name, module in [('conv', (net.conv1, net.conv2, net.conv3)),
                     ('fc', (net.fc,)), ('head', (net.value, net.advantage))]:
    print(name, sum(p.numel() for m in module for p in m.parameters()))
```

本项目改造前：

| 层 | 参数 | 占比 | 干什么 |
|---|---|---|---|
| conv1+2+3 | 77,984 | **6.2%** | 全部的空间理解 |
| fc(2304→512) | 1,180,160 | **93.7%** | 一次线性压缩 |
| value+advantage | 1,539 | 0.1% | 输出 |

**94% 的参数在一个全连接层上。** 这是卷积网络的典型形态（卷积靠权值共享，
参数极少；全连接是输入维×输出维），但比例这么极端时值得追一下：
那 118 万参数真的被用到了吗？

---

## 2. 诊断三：网络实际用了多少维

参数量大不等于容量被用上。直接测**激活的有效维度**：

```python
# 在真实观测上跑 N 次前向，收集每层激活
X = np.array(activations)              # (N, dim)
dead = (X.max(0) <= 1e-8).sum()        # 从来不激活的单元
s = np.linalg.svd(X - X.mean(0), compute_uv=False)
ratio = np.cumsum(s**2) / (s**2).sum()
eff95 = np.searchsorted(ratio, 0.95) + 1   # 95% 方差需要几个主成分
```

本项目在 4000 次真实观测上的结果：

| 模型 | 层 | 维度 | 死单元 | 95% 方差 | 99% 方差 |
|---|---|---|---|---|---|
| gpu_random1 | conv3 | 2304 | 5 (0.2%) | 604 | 1279 |
| | **fc** | **512** | **72 (14.1%)** | **113** | **209** |
| gpu_random3 | conv3 | 2304 | 0 (0%) | 800 | 1460 |
| | **fc** | **512** | **130 (25.4%)** | **92** | **177** |

怎么读：

- **卷积栈是满的**：几乎零死单元，有效维度 604–800。它只占 6.2% 的参数，
  却在真干活。**不要动它。**
- **fc 层明显冗余**：14–25% 的单元从不激活；512 维的激活实际活在
  约 100 维的子空间里，99% 的方差也只要 177–209 维。
- **更难的任务反而用得更少**（25.4% vs 14.1% 死单元）。这条特别有说服力：
  **如果容量是瓶颈，难任务应该榨干网络，而不是用得更少。**

由此看起来能得到一个"有依据"的取值：**fc 512 → 256**（256 > 99% 所需的 209）。

> **剧透：这个推论只对了一半。** 本文末尾的 2×2 对照实验显示，
> 砍 fc 在 80×128 的观测下无害，在 80×80 下却会掉 30–60%。
> 上面这些数字恰恰是在 80×80 的模型上测的。
> 为什么会这样、以及该吸取什么教训，见第 6 节之后的附录。

## 3. 三个诊断的结论落到代码上

### 改动一：各向异性观测

任务的精度需求几乎全在**竖直**方向（对准缝隙），而原来 288×512 的屏幕
被压成正方形的 80×80——竖直压 6.4 倍、水平只压 3.6 倍，**恰好压错了方向**。

改成 `80 宽 × 128 高`：

| | 80×80 | **80×128** |
|---|---|---|
| 竖直压缩 | 6.4× | **4.0×** |
| 60px 缝隙在观测里 | 3 个像素行 | **5 个** |
| 100px 缝隙 | 6 行 | **10 行** |
| 165px 缝隙 | 11 行 | **18 行** |

> **一个容易搞反的坑**：`pygame.surfarray` 是 width-major，
> `pixels3d(SCREEN)` 返回 `(288, 512, 3)` = (屏幕宽, 屏幕高, 通道)。
> 所以观测数组的 axis 0 是**屏幕宽**、axis 1 是**屏幕高**，画面在数组里是转置的。
> 要让竖直方向变成 128，`cv2.resize` 的 dsize 必须写 `(obs_h, obs_w)`。
> 卷积网络不在乎哪边是"上"，但形状写反了会静默地把分辨率加到错误的轴上。

### 改动二：fc 512 → 256

### 两项一起的效果

```
旧  80×80  fc512   conv输出 (64, 6, 6)   展平 2304   参数 1,259,683
新  80×128 fc256   conv输出 (64, 6,12)   展平 4608   参数 1,258,659
```

**参数量几乎完全相同（差 0.08%）**——竖直分辨率翻倍和 fc 减半正好抵消。
同样的预算，花在了有证据支持的地方。

### 改结构时别手算展平维度

```python
def conv_out(size, kernel, stride, padding=0):
    return (size + 2 * padding - kernel) // stride + 1

h = conv_out(conv_out(conv_out(in_h, 8, 4), 4, 2), 3, 1)
w = conv_out(conv_out(conv_out(in_w, 8, 4), 4, 2), 3, 1)
self.flat_dim = 64 * h * w
```

写死 `64*6*6` 的话，换分辨率时要等到第一次前向才报形状错误——
而且如果碰巧维度对上了（比如同时改了两个地方），会静默地训出一个错的东西。

---

## 4. 一个必须保留的怀疑

**有效维度低说明"训练出来的解"是低秩的，不等于"用更小的网络从头训"也能到达同一个解。**

过参数化对**优化过程本身**有帮助——更大的参数空间里，好解的吸引域更大、
鞍点更容易逃离。这是深度学习里被反复观察到的现象。
所以上面的诊断只能说明**冗余存在**，不能直接推出**删掉安全**。

要坐实必须跑对照训练：两个配置只差 fc 宽度，其余（观测、超参、随机种子、
环境分布）全部相同。本项目的做法：

```bash
python train.py --gap-range 70 165 --fc-hidden 256 --run-dir runs/fc256
python train.py --gap-range 70 165 --fc-hidden 512 --run-dir runs/fc512
```

> 结果见本文末尾。**在拿到对照结果之前，不要把"参数冗余"当成"可以删"。**

---

## 5. 什么时候该真的加大网络

上面全在讲"别急着加大"，但确实有该加的信号：

| 信号 | 含义 |
|---|---|
| 死单元接近 0 **且** 有效维度接近层宽 | 容量被榨干了，加宽可能有用 |
| 训练 loss 降不下去（不是 TD 噪声，是拟合不了） | 表达能力不足 |
| 完美状态对照**也**只是略好 | 瓶颈不在感知，加大网络多半没用 |
| 更难的任务用**更多**容量 | 容量确实是约束 |

本项目四条全部指向反面，所以结论是"该删不该加"。

---

## 6. 诊断清单

改网络之前，按顺序问：

1. **瓶颈在哪一环？** 跑完美状态对照 → 分清物理 / 感知 / 容量 / 优化
2. **参数花在哪？** 一行代码统计每层占比 → 找出异常集中的层
3. **实际用了多少维？** 死单元 + PCA 有效维度 → 量化冗余
4. **难任务用得更多还是更少？** 用得更少 = 容量不是瓶颈
5. **改完跑对照了吗？** 只差一个变量，其余全部固定

跳过任何一步，你就是在猜。

## 附：本项目的 2×2 对照实验

四格只差两个变量（观测分辨率、fc 宽度），其余全部相同：
`gap_range=70-165`、`buffer=35000`、`eps_start=1.0`、
`anneal1=250000`、`anneal2=350000`、`seed=0`、约 19000 局。
每格 **100 局纯贪婪评测**，单局上限 3000 决策。

| 观测 | fc | 参数 | 训练分布<br>gap 70–165 | 更窄 gap 60–80<br>*未训练过* | 固定 gap 100<br>*未训练过* |
|---|---|---|---|---|---|
| **80×128** | **256** | 1,258,659 | **30.7** | 3.0 | **162.9** |
| 80×128 | 512 | 2,439,331 | 29.8 | 3.3 | 158.8 |
| 80×80 | 256 | 668,835 | 19.4 | 2.3 | 22.5 |
| 80×80 | 512 | 1,259,683 | 27.7 | 2.5 | 58.1 |

### 结论一：各向异性分辨率有效，泛化上尤其明显

固定 fc 横向比：

| | 80×80 | 80×128 | 提升 |
|---|---|---|---|
| fc256 训练分布 | 19.4 | 30.7 | **1.6×** |
| fc512 训练分布 | 27.7 | 29.8 | 1.1× |
| fc256 固定 gap 100 | 22.5 | **162.9** | **7.2×** |
| fc512 固定 gap 100 | 58.1 | **158.8** | **2.7×** |

训练分布上只涨 1.1–1.6 倍，但在**没训练过**的固定 gap 100 上涨 2.7–7.2 倍。
高分辨率模型学到的更像是几何关系，低分辨率模型更像是拟合特定分布的窍门。

第 0 节的完美状态对照预测宽缝上有 **2.5 倍**空间，实测泛化场景 2.7 倍 ——
**预测得相当准，这也是那个诊断值得先做的理由。**

### 结论二：fc 能不能砍，取决于分辨率（没预料到的交互作用）

| | fc512 → fc256 |
|---|---|
| 80×128 训练分布 | 29.8 → **30.7** ✅ 无害 |
| 80×128 固定 gap 100 | 158.8 → **162.9** ✅ 无害 |
| 80×80 训练分布 | 27.7 → **19.4** ❌ 掉 30% |
| 80×80 固定 gap 100 | 58.1 → **22.5** ❌ 掉 61% |

**同一个"砍掉一半 fc"的改动，在高分辨率下无害，在低分辨率下掉三到六成。**

一个合理的解释：80×80 的观测把信息压没了，网络需要额外参数去补偿；
80×128 把信息给足之后表示变干净，fc 就不需要那么宽。
换句话说 —— **那些"冗余"参数其实在补偿感知不足。**

> ### 这推翻了第 2 节推论的一半
>
> 第 2 节测出 fc 有 14–25% 死单元、95% 方差只占约 100 维，据此建议砍到 256。
> **那个测量是在 80×80 的模型上做的，而在 80×80 下砍 fc 恰恰是有害的。**
>
> 所以"有效维度低"这个信号**不能单独使用**：它告诉你训练出来的解是低秩的，
> 但没告诉你那些多余的参数在优化过程中起了什么作用。
> 第 4 节的保留意见是对的，而且比我写的时候以为的更重要。
>
> **教训：容量诊断必须和感知诊断一起看，单独做会给出错误建议。**

### 结论三：物理边界改不动

gap 60–80 上四格全部落在 2.3–3.3，分辨率和容量都无效。
与第 0 节完美状态 MLP 的结果一致 —— 那是控制/物理的限制
（小鸟最小悬停振荡 22.5px，而 60px 缝隙扣掉鸟高只剩 36px），
不是网络能解决的问题。

### 最优配置

**80×128 + fc256**：三项里两项最好，参数比原来的 80×80 + fc512
还少 1024 个。同样的预算，换来 1.1 倍的训练分布性能和 2.8 倍的泛化性能。

### 这个实验的局限

- **只有一个随机种子。** 四格用同一个 `seed 0`，消除了初始化和环境序列
  的方差，但没排除"这个种子恰好偏袒某个配置"。严格的做法是每格跑 3–5 个
  种子取平均，代价是 5 倍机时。
- **只测了两个分辨率、两个 fc 宽度。** 交互作用的存在说明网格再密一点
  可能还有更好的点。
- **收敛问题见下节** —— 后来专门跑了一轮长训练来回答它，
  结果比预想的复杂。

## 附二：训练分布上的指标会掩盖泛化的进步

2×2 的四格都只跑到约 19000 局，当时的疑问是"是不是没收敛"。
于是用胜出配置（80×128 + fc256）单独跑了一轮 **25550 局**，
其余配置完全相同，中途每 500 局记录一次。

### 从训练侧看，它在 ep 20000 就平了

| 局数区间 | 近百局均分 | 贪婪评测（20 局）|
|---|---|---|
| 17000–18500 | 26.14 | 30.96 |
| 19000–20500 | 25.20 | 41.73 |
| 21000–22500 | 26.08 | 38.60 |
| 23000–25000 | 26.43 | 37.83 |

`recent100` 四段全在 25–26.5 之间纹丝不动，Q 均值也从 11.4 爬到 11.8 就基本停了
（理论上限 12.6）。按这些指标判断，**ep 20000 之后的 5000 多局是白跑的**。

### 但 100 局跨环境评测说的完全相反

| 模型 | 训练分布<br>gap 70–165 | gap 60–80<br>*未见* | 固定 gap 100<br>*未见* | gap 100–165<br>*未见* |
|---|---|---|---|---|
| **25550 局** | **30.8** | 3.1 | **218.0** | **181.3** |
| 17200 局 | 30.7 | 3.0 | 162.9 | 127.2 |
| 差异 | **+0.3%** | +3% | **+34%** | **+43%** |

**训练分布上完全持平，两个未见分布上涨了 34% 和 43%。**

### 为什么会这样

训练分布 `gap 70-165` 里混着 70–80px 的窄缝，那是[物理墙](11-generalization.md)——
无论策略多好都过不去，于是这些局的分数被钉死，把均值也钉住了。
而在没有窄缝的分布上，策略的真实改进才显现出来。

> **教训：用训练分布上的指标判断"还该不该练"，会漏掉泛化维度的进步。**
>
> 尤其当训练分布里含有智能体**注定失败**的一部分时，那部分会给均值加一个
> 恒定的天花板，让还在改进的策略看起来已经停滞。
>
> 判断收敛应当**同时**看训练分布和至少一个未见分布。本项目的
> `eval.py --gap-range` / `--no-randomize` 就是为此准备的。

### 现在的基线

| | 值 |
|---|---|
| 配置 | 80×128 + fc256，1,258,659 参数 |
| 训练 | 25550 局 / 200 分钟（RTX 3070 Laptop）|
| 训练分布 gap 70–165 | 30.8 |
| 固定 gap 100 | **218.0**（24% 的局跑满 3000 决策上限仍活着）|
| gap 100–165 | 181.3 |
